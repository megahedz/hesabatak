# حساباتك — حسابات مشروعك ببساطة

## الحالة الحالية (نهاية Phase 4 — Auth حقيقي)

### ما تم إنجازه وتشغيله واختباره فعليًا (Phase 1 → 4):

**من Phase 1+2:** محرك محاسبي مستقل بكل العمليات الثمانية، دليل حسابات
تلقائي، تقارير من القيود مباشرة، عملاء/موردين وكشوف حساباتهم، ترقيم فواتير.

**من Phase 3:** واجهة Flutter كاملة (Bottom Nav، شاشات العملاء/الموردين،
العمليات الثمانية، التقارير بثلاثة تبويبات).

**جديد في Phase 4 — Auth حقيقي:**
1. **تسجيل مستخدمين حقيقي** (`/auth/register`, `/auth/login`) — كلمة مرور
   مشفّرة (bcrypt)، JWT صالح لمدة أسبوع.
2. **كل نقطة API الخاصة بشركة محمية الآن**: تحتاج Token صالح + أن يكون
   المستخدم عضوًا فعليًا في هذه الشركة تحديدًا (وليس فقط مسجّل دخول). محاولة
   الوصول لشركة مستخدم آخر تُرفض بـ 404 (بدون تأكيد إن كانت الشركة موجودة
   أصلًا — لا تسريب معلومات).
3. **من ينشئ شركة يصبح مالكها تلقائيًا** (`company_users`، role='owner').
4. **حارس أمان عند التشغيل**: السيرفر **يرفض العمل** إذا كان `HESABATAK_SECRET_KEY`
   غير مضبوط بيئيًا، إلا بتفعيل صريح لوضع التطوير — تم اختباره فعليًا (رأينا
   الخطأ يُرمى وإيقاف الإقلاع عند عدم ضبط المتغير).
5. **7 اختبارات auth جديدة عبر HTTP فعلي** (TestClient لا استدعاء دوال مباشر):
   تسجيل، دخول خاطئ مرفوض، مسار محمي بدون Token مرفوض بـ 401، منشئ الشركة
   يصير مالكها، **مستخدم آخر لا يصل لشركة غيره حتى برمز صالح خاص به**، قائمة
   "شركاتي" تعرض شركات المستخدم فقط، ورقم هاتف مكرر مرفوض. **17/17 اختبار ناجح**.
6. **واجهة Flutter مربوطة بالكامل بالـ Auth**: شاشة دخول/تسجيل، اختيار أو
   إنشاء أول شركة تلقائيًا بعد التسجيل (بأسلوب onboarding من البند 56/57)،
   وزر تسجيل خروج، والتوكن يُرفق تلقائيًا مع كل طلب.

### حدود بيئة هذا العرض (مهم توضيحه بصراحة):
- تم **تشغيل واختبار** الـ Backend فعليًا هنا، بما فيه اختبار حي عبر curl
  لتسجيل مستخدمين حقيقيين، إنشاء شركة، والتأكد أن مستخدمًا آخر يُرفض بـ 404.
- كود Flutter **مكتوب فعليًا ومُراجَع سطرًا بسطر** لكن **لم يُجمَّع (compile)
  أو يُشغَّل هنا** — شغّله على جهازك للتأكد النهائي.
- **الجلسة (Token) في الذاكرة فقط حاليًا** — إغلاق التطبيق يسجّل خروج
  المستخدم تلقائيًا. حفظها بشكل دائم (flutter_secure_storage) هو أول شيء
  في Phase 5، وتم تصميم AppSession بحيث لا تغيير في باقي الشاشات عند إضافته.
- حالة حافة بسيطة غير مصقولة: لو أنشأ المستخدم حسابًا ثم ألغى اسم الشركة في
  الـ dialog الأول (ترك الحقل فارغًا)، يعود لشاشة الدخول ويحتاج تسجيل الدخول
  مرة أخرى ليُعاد عرض الـ dialog. لا يفقد أي بيانات، لكنها تجربة مستخدم
  تحتاج صقلًا لاحقًا (شاشة "إنشاء شركة" منفصلة بدل dialog داخل شاشة الدخول).

## تشغيل الـ Backend محليًا

```bash
cd backend
python -m pip install -r requirements.txt
export HESABATAK_SECRET_KEY="ضع-مفتاحًا-عشوائيًا-طويلًا-هنا"
# أو للتجربة السريعة فقط: export HESABATAK_ALLOW_DEV_SECRET=1
python -m uvicorn app.main:app --reload
# افتح http://127.0.0.1:8000/docs لتجربة كل الـ endpoints
```

لتشغيل الاختبارات:
```bash
cd backend
pytest app/tests/ -v
```

## تشغيل الـ Flutter app محليًا
```bash
cd mobile
flutter pub get
flutter run
# غيّر AppConfig.apiBaseUrl في lib/core/app_config.dart حسب عنوان جهازك
# (10.0.2.2 يعمل تلقائيًا لمحاكي Android على نفس الجهاز)
# أو مرّر: flutter run --dart-define=API_BASE_URL=http://192.168.1.x:8000
```
لا حاجة لإنشاء شركة يدويًا عبر `/docs` بعد الآن — أول تشغيل للتطبيق يمرّ
بشاشة تسجيل، ثم يطلب اسم أول مشروع/محل تلقائيًا.

## الفرضيات (Assumptions) المُتخذة (بند 81 — قرار مهني بدل التوقف)
- استخدمنا SQLite للتطوير/الاختبار المحلي؛ الانتقال لـ PostgreSQL في
  السيرفر (عند إضافة المزامنة السحابية) تغيير في سطر واحد (`DATABASE_URL`).
- الخزينة والبنك في المرحلة الأولى: حساب واحد لكل منهما لكل شركة (وليس
  حسابات نقدية/بنكية متعددة) — أبسط للمستخدم غير المحاسب، وقابل للتوسع لاحقًا.
- الشراء الافتراضي (بدون تحديد `goes_to_inventory=true`) يُرحَّل مباشرة إلى
  تكلفة البضاعة المباعة، لأنشطة الخدمات التي لا تحتفظ بمخزون؛ الأنشطة التي
  تبيع منتجات فعلية يجب أن تمرر `goes_to_inventory=true` عند الشراء (شاشة
  الشراء في Flutter فيها Checkbox لهذا بالضبط).
- تكلفة البضاعة المباعة (COGS) عند البيع تُمرَّر كقيمة محسوبة عند نداء
  `create_sale()`؛ حساب Weighted Average التلقائي من حركة المخزون سيُضاف
  في مرحلة المخزون (Phase 4) دون تغيير شكل الـ Accounting Engine.
- تم ربط سطور القيد المحاسبي (journal_entry_lines) مباشرة بـ customer_id/
  supplier_id عند البيع/الشراء الآجل والتحصيل/السداد — هذا يجعل مستقبلًا
  بناء "كشف حساب" من القيود مباشرة (وليس فقط من جداول الفواتير) ممكنًا.
- شاشة التحويل بين الحسابات مبدئيًا بين الخزينة والبنك فقط (أكثر حالة
  استخدامًا)؛ التوسع لحسابات نقدية/بنكية متعددة يأتي مع البند السابق عن
  cash_accounts/bank_accounts.

## الخطوة القادمة (Phase 5 حسب الخطة المعدّلة)
حفظ الـ Token بشكل دائم في Flutter (flutter_secure_storage) بحيث لا يحتاج
المستخدم تسجيل الدخول كل مرة، ثم المخزون والـ VAT (البنود 18 و33)، ثم بقية
التقارير (General Ledger، Cash Flow، تقارير المبيعات/المشتريات/المخزون)
وتصدير PDF/Excel.
